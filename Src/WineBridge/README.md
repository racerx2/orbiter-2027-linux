# WineBridge (Src/WineBridge)

Windows modules (.dll) in Linux Orbiter: the DLL runs in a small Wine helper, Orbiter talks to it through shared memory.

- `linux/`: `Modules/WineBridge.so`. Orbiter opens a Windows module through it wherever it finds a `.dll` and no `.so` of that name (vessel classes, plugins, startup modules): an add-on installs as on Windows, with no change to its files (`wbModuleLoad`, `wbModuleProc`, `wbModuleFree`, linux/Slots.cpp). A class whose cfg says `Module = WineBridge` and `WineModule = <the .dll, Orbiter-relative or absolute>` still works.
- `helper/`: `Modules/WineBridge/Orbiter.exe`, a 32-bit Windows program built with clang for i686-windows against the Orbiter 2024 SDK headers (`sdk/win32`, MIT). It exports the Orbiter API under the names the DLLs import from `Orbiter.exe`. A module built with the 2010 SDK gets the 2010 layouts of the classes that changed (Sketchpad, the lights: `helper/compat2010.h`); the module's API date (GetModuleVersion) tells which. Modules is on the helper's DLL search path, as Orbiter puts it on PATH.
- `proto/`: the channel both sides share.
- `api/imports.txt`: every name a Windows module may import from `Orbiter.exe` (tools/apilist.py: the 2010 and 2016 exes' export tables, `api/exports2010.txt` and `api/exports2016.txt`, and the 2024 SDK's exported declarations; the graphics client's parts left out). `api/later.txt` lists those not bridged yet, each with the stage that brings it; a module importing one is refused and the log names it.
- `tools/wbgen.py`: the build generates both sides of most functions from the Windows and the Linux SDK headers (libclang); `api/manual.txt` lists the ones written by hand, `api/strings.txt` how char * parameters cross. A function the Linux SDK declares but this Orbiter doesn't define is left out (`gen/absent.txt`). The build stops when a name of the list is neither exported nor in those lists (tools/coverage.py).
- `tests/probe.cpp` (`-DWB_TESTS=ON`): a test plugin; `WB_PROBE=trace` writes every vessel's state, beacons, exhausts and lights frame by frame (the options are at the top of the file), to compare a DLL through the bridge with a native build of it.

Build: Orbiter's build makes it when the tools are there (cmake/winebridge.cmake: an ExternalProject against the build tree, installed into it; `-DORBITER_WINEBRIDGE=OFF` leaves it out): Wine's headers and i386 import libraries (Wine 11), clang, lld, python3 with clang.cindex, Qt 6 (Gui), and git with network at configure time (Orbiter's zlib and Lua are fetched, as Orbiter's build does). On its own: `cmake -S Src/WineBridge -B <dir> -G Ninja -DORBITER_ROOT=<Orbiter folder>`, then `ninja -C <dir>` and `cmake --install <dir>`. The build stops when an import of `api/imports.txt` isn't bridged (`-DWB_REQUIRE_ALL=OFF` builds anyway).

Package: packaging/linux/rc.sh builds the Windows files and the generated calls on the PC, against the release root's build tree, then the Linux module in the root from that build (`-DWB_HELPER_FROM=<build>`, refused for a build against another Orbiter) with GCC 14 and the package's Qt; collect.py checks it with every file. `doc/README.txt` is installed as `Doc/WineBridge/README.txt` and tells users which Wine to install. Running needs a Wine that runs 32-bit programs; tested are Linux Mint 22.3's Wine 9.0 (with wine32) and WineHQ's 11. When the helper ends before it answers, Orbiter.log gets Wine's failure lines from WineBridge.log; a prefix made while Wine had no 32-bit part is updated at the next start.

Entry points Orbiter calls by name: GetModuleVersion, ModuleDate, ovcInit, ovcExit and the opc callbacks of legacy plugins; InitModule and ExitModule run in the helper as Orbitersdk.lib's DllMain runs them. A vessel whose module object is a plain VESSEL (version 0) has that version in Orbiter too: it gets no callbacks, as on Windows. A module is freed when Orbiter frees its last open, as FreeLibrary does, and the helper stops when no module is open.

Step 2 bridged every Orbiter.exe import of 16 DLLs of 2010 vessel add-ons and ShuttlePB: vessel states, scenarios, beacons and exhausts Orbiter reads every frame, lights, mesh copies, other vessels, airfoil and lift functions, 2D panels, virtual cockpits, HUDs through Sketchpad, GDI drawing on surfaces (oapiGetDC), bitmaps. A DLL that imports anything else is not loaded; Orbiter.log names what is missing.

MFD modes, MFDs and plugin module objects: a module's MFD mode is registered with Orbiter under its name and key; each MFD object the mode makes has a proxy in Orbiter (an MFD2 through a sketchpad, an MFD through GDI on a copy of the display), and so do external MFDs and oapi::Module objects. The MFD, MFD2, GraphMFD, ExternMFD and Module classes are the helper's (`helper/mfd.cpp`, `module.cpp`), their inline members exported by name (`api/inline.def`). The helper has orbiter.exe's manifest dependencies (VC80 and VC90 runtimes, Common Controls 6), which modules without a manifest of their own rely on.

HDC HUD: a module's HUD drawn with GDI (a VESSEL2 module's, or after a sketchpad HUD that returns false, as Orbiter 2016 called it) is drawn on an enhanced metafile DC; its records are then drawn with Orbiter's HUD sketchpad (`helper/hud.cpp`).

Celestial bodies and atmospheres: a body module's object (InitInstance) and an atmosphere module's (CreateAtmosphere) have proxies in Orbiter that forward the virtual methods their classes override. CELBODY2's own methods run on the proxy, so Orbiter loads the body's atmosphere module, native or Windows, and the module object's `atm` member follows the proxy's. ExitInstance and DeleteAtmosphere are always answered; without the module's function its operator delete frees the object, as Orbiter's delete did. The 2006 interface (`<body>_Ephemeris` and the others) goes through a pool of bound functions; oapiGetCelbodyInterface gives a module the helper's object for a native body. The Launchpad's atmosphere list reads a Windows module's ModelName and ModelDesc through the bridge (`helper/celbody.cpp`, `linux/Celbody.cpp`).

Launchpad items, custom commands, camera control and modes, help: a module's Launchpad item has a proxy in Orbiter's Extra tab (its name and description read from the module's object, Open and WriteConfig forwarded); its custom commands are bridge functions that call the module's; its external camera control has a proxy Orbiter polls, its modes read from the object every helper call (live items), dropped with the camera that held it (the core's `wbCameraControlGone`). CameraMode and its classes are the helper's, with the 2010 layouts of CameraMode_Cockpit and CameraMode_Ground for 2010 modules; Create allocates with the calling module's own operator new; oapiSetCameraMode sends the mode's fields (`helper/lpad.cpp`, `camera.cpp`, `linux/Extra.cpp`). A Launchpad item's dialog (OpenDialog) is modal, as on Windows: the Launchpad waits.

Text: Orbiter shows UTF-8, a Windows module's text is in its ANSI code page (Wine's, from the locale), as released Orbiter was ANSI. Its text Orbiter shows (Launchpad items, custom commands, the input box, log lines, sketchpad and HDC HUD text, annotations, the debug line) crosses in UTF-8: kept when it is UTF-8 already, converted otherwise; the text typed in an input box goes back in its code page (`helper/text.cpp`; `text` in `api/strings.txt` for generated functions). Names, paths and file contents cross as bytes.

Meshes, panels, airfoils: a mesh a module makes (oapiCreateMesh, groups and blocks added) is Orbiter's; the module's copies of its groups are read again after a block is added and dropped with the mesh. oapiRenderHUD sends as many of the module's textures as the client reads for the mesh. A VESSEL3 2D panel's background, scaling and areas of all three forms are Orbiter's; an area's context is kept per vessel and comes back to the module in the panel callbacks. CreateAirfoil2 and CreateAirfoil4 (force and moment), EditAirfoil (a new function too) and GetAirfoilParam go through the bridge's airfoil records; oapiGetNavData gives the transmitter's id string from a copy kept per transmitter (`linux/Panel.cpp`).

Lights: the helper's object of each light Orbiter has (AddPointLight, AddSpotLight, GetLightEmitter) holds the light's state as the module's object does on Windows, in its SDK's layout (2010's has no visibility); after every change its state goes to Orbiter's light, the *Ref pointers as live items of the module's memory; a change with no setter (an inline SetVisibility, a member-wise assignment the module compiled in) goes at the end of the helper's call. The inline and compiler-made members Orbiter.exe exports read the light in its layout. GetLightEmitter of another vessel's light gives a copy filled at each call. DelLightEmitter and ClearLightEmitters delete Orbiter's lights first (`helper/light.cpp`, `linux/Light.cpp`). The drawing tools', sketchpad's and vessel classes' inline and compiler-made members are exported from `helper/made.cpp`; the helper is a Release build, as Orbiter.exe (the SDK's sketchpad defaults assert otherwise).

Beacons, exhausts, animations: GetBeacon and GetExhaustSpec give a module back its own beacon spec and its own level, position and direction pointers, other values as the helper's copies; DelBeacon and ClearBeacons stop the helper reading the module's specs. Objects of a module Orbiter keeps reading are watched: a 2006 animation component (AddAnimComp) and the transforms of AddAnimationComponent go again when they change, at the end of the helper's call. GetAnimPtr gives a copy of Orbiter's animations, with the module's own transforms; Orbiter's states come into it before each call from Linux, and a state the module writes into it goes into Orbiter's array (`helper/vdata.cpp`, `linux/Vdata.cpp`).

Orbiter's data: a value a module gets a pointer to (oapiGetObjectParam, file names, the command line) is the helper's copy, kept per object. oapiObjectVisualPtr gives a slot per body that the helper sets from Orbiter's visual before each call from Linux. oapiInflate and oapiDeflate run in the helper with Orbiter's zlib (fetched at configure time, as Orbiter's Extern/zlib), as in Orbiter.exe.

Script interpreter: Windows modules get Orbiter 2024's own: `Modules/WineBridge` has lua.dll (Orbiter's Lua, fetched as Orbiter's Extern/Lua), lua5.1.dll forwarding to it for 2010 and 2016 modules, and LuaInterpreter.dll and LuaInline.dll built from the 2024 release's source (`lua/`, MIT; the bridge's changes marked "not upstream"). oapiCreateInterpreter and the others work as Orbiter.exe's: the first has Orbiter load LuaInline as a plugin (the core's `wbPluginLoad`), whose callbacks then run the interpreters. A module's class derived from Interpreter with the 2010 or 2016 header has its virtual functions in that version's order: the interpreter calls them by the class's version (its maker's SDK date, checked against the class's table; `lua/wb_interp.cpp`), and LuaInterpreter.dll exports the 2010 and 2016 names (`api/luainterp.txt`, checked at build time). The xrsound Lua library isn't in it: a Windows module's script has no xrsound table.

Dialogs: Orbiter 2024's dialog manager in the helper (`helper/dialog.cpp`): oapiOpenDialog(Ex), oapiFindDialog, oapiCloseDialog, oapiGetDialogContext, oapiRegisterWindow and the title buttons, while a simulation runs (the core's dialog manager tells the bridge when it is made, cleared and deleted, and the helper posts its broadcasts to the modules' dialogs). The dialogs and any window a module makes are Wine's windows on the desktop, not owned by Orbiter's window; the helper keeps DISPLAY and WAYLAND_DISPLAY, but for an Orbiter running offscreen. Their messages are dispatched (H_PUMP) from a 15 ms timer whenever no bridged call is under way: in the Launchpad, in flight and paused alike. A modal dialog runs its own loop inside the call that opened it, and Orbiter waits, as on Windows. Orbiter.exe's WndProc and LaunchpadVideoWndProc, which only graphics clients forward to, give Wine's default.

A module's Lua methods for Orbiter's scripts: a vessel's VMSG_LUAINTERPRETER and VMSG_LUAINSTANCE give the module Linux's Lua state as a remote state, the helper's object for it. lua.dll's API functions (`lua/wb_luaapi.c`, Lua's own renamed by `lua/wb_rename.h`) send a remote state's calls to Linux (`helper/luaremote.cpp`, `linux/Lua.cpp`), so Lua's libraries and the module work on it as on its own. The module's C functions are closures of the bridge's on Linux that call them in the helper. A Lua error unwinds the module's frames up to the call from Linux, as on Windows, and Linux raises it again; the calls Lua may raise in run there in lua_pcall. Strings and copies of Linux's userdata stay valid until the outermost call from Orbiter returns; a module's own userdata is its memory, freed when Lua collects Linux's userdata that stands for it. Lightuserdata of the helper's memory stay as they are, others are the bridge's handles. Precompiled chunks are rewritten between the helper's 32-bit Lua and Linux's 64-bit one. The other way, a Windows module's interpreter gives a native vessel its state as a remote one (the core's lua.so sends a remote state's calls to the functions the bridge registers with `lua_setremote`; `linux/LuaRemote.cpp`, `helper/luaserve.cpp`), so a script there sees a native vessel's Lua methods as on Windows. lua_tointeger rounds as the vessel module's Lua does.

Vessel hooks: a module that patches the vtable of a vessel's class (as VesselHooking.dll does for HUDDrawer) works as on Windows. The helper's object for a Linux vessel forwards all its callbacks to the vessel's own and has a copy of its vtable per Linux class, put back when the class's last vessel is gone; at the end of each call from Orbiter the helper compares the vtables it watches (`helper/hooks.cpp`). Orbiter then calls a hooked callback of a Linux vessel through the helper (`linux/Hooks.cpp`, with the core's `wbVesselIntf`), and a bridged vessel's through the module's object.

OrbiterSound: when XRSound is loaded (checked at each module load), the helper loads `Modules/WineBridge/OrbiterSound.dll`, which the OrbiterSound SDK in the modules finds as it finds the OrbiterSound plugin on Windows; its vessel, MFD and radio sounds, stock sound replacements and options play through XRSound (`linux/Sound.cpp`). There is no 3D sound: XRSound has none.

XRSound: with it the helper loads `Modules/WineBridge/XRSound.dll`, which the XRSound SDK in the modules finds as it finds XRSound.dll on Windows. Its engines are Linux XRSound's, a vessel's or a module's, each method sent to Linux (`helper/xrsound.cpp`, `linux/Sound.cpp`); XRSound's version is Linux's. An engine stops answering when XRSound destroys it: after its vessel goes and at the session's end.

`ORBITER_WB_PROFILE=1` logs, with each 10 s report, the calls that took the most time. `ORBITER_WB_WINEDEBUG` sets Wine's debug channels for the helper (default `-all,err+module`; `+seh` shows where a Windows module faults), written to WineBridge.log.
